# releasing

This covers the release pipeline: the PR label it reads, the two workflows, the two secrets, cargo-dist, and building from source. See the [README](../README.md) for installing and a quick start.

Two workflows run one after the other. `version-tag.yml` reads the version label on a merged pull request, bumps `[workspace.package] version`, rolls the changelog, and pushes the commit and a `vX.Y.Z` tag. `release.yml` is generated by [cargo-dist](https://opensource.axo.dev/cargo-dist/) from `dist-workspace.toml`, triggers on that tag, builds three archives, creates the GitHub release and pushes a `teamzones.rb` formula to `paulchiu/homebrew-tap`.

## The version label

A pull request needs exactly one of `major`, `minor`, `patch` or `norelease`, and the `Enforce Semantic Versioning` check fails it until it has one. After the merge, `version-tag.yml` bumps by whichever of `major`, `minor` or `patch` is set; `norelease` merges and bumps nothing.

`minor` is for anything a user could not do before, and for a breaking change while the major version is held at 0. `patch` is for a fix or a tightening. `norelease` is only for docs or CI changes nobody using the tool can see. Nobody runs `cargo set-version` by hand, because two branches bumping off the same `main` would collide.

## The changelog

Each pull request with a change someone would notice adds its lines under `## [Unreleased]` in `CHANGELOG.md`, under `### Added`, `### Changed`, `### Fixed` or `### Removed`. On merge, `version-tag.yml` renames that heading to `## [X.Y.Z] - YYYY-MM-DD` and puts a bare `## [Unreleased]` back above it. cargo-dist uses that version's section, as written, for the GitHub release notes, which is why a pull request adds only the subsections it needs.

## Secrets

Two repository secrets, both personal access tokens:

| Secret | Why |
| --- | --- |
| `RELEASE_TOKEN` | A tag pushed with the default `GITHUB_TOKEN` starts no further workflows, so `release.yml` would never see it. Needs `contents: write` on this repository. |
| `HOMEBREW_TAP_TOKEN` | The name cargo-dist expects for the token its publish job checks the tap out with. Needs `contents: write` on `paulchiu/homebrew-tap`. |

Without `RELEASE_TOKEN` the bump and the tag still land and the release has to be started by hand. Without `HOMEBREW_TAP_TOKEN` the GitHub release is still built and only the formula push fails.

## What a release produces

One archive each for `aarch64-apple-darwin`, `x86_64-apple-darwin` and `x86_64-unknown-linux-gnu`, each holding the binary, the changelog, the licence and the README, plus checksums and the formula. macOS gets one archive per architecture rather than a universal binary, because Homebrew picks the one matching the machine it installs on.

`brew install paulchiu/tap/teamzones` is the tap and the formula in one line; `brew tap paulchiu/tap` then `brew install teamzones` does the same in two.

## Changing the release workflow

Never edit `release.yml` by hand. Change `dist-workspace.toml` and run `dist generate`, because dist's own plan step on every pull request fails when the workflow no longer matches the config. The same goes for a Dependabot pull request that bumps an action inside it: pin the action under `[dist.github-action-commits]` instead, as `actions/checkout` is, and drop the pin once dist's own default catches up.

## Building from source

```sh
just ci                           # format, lint, test, docs, core isolation, build
just workflows                    # parse every workflow (needs PyYAML)
cargo install --path crates/teamzones
```

`just ci` is what the CI workflow runs, so a green run here is a green pipeline. It includes `check-core-isolation`, which holds `teamzones-core`'s direct dependencies to an allowlist so a terminal or clipboard crate can never reach the core.
